# Gotchas

## Site build (verified 2026-09-24)

- CI never rebuilds the OG share cards. `.github/workflows/generate-site.yml` runs `npm test` and `scripts/generate-site.js`, not `scripts/generate-og-images.js`. After changing a plugin's version or description, run `npm run generate` and commit the PNGs, or the card goes stale.
- `npm test` rewrites `docs/`, because `tests/generate-site-redesign.test.js` runs the generator when it loads.
- The OG card wraps a description at 52 characters and cuts it at three lines. Keep `description` under about 150 characters.
- A listing row shows only a plugin's first three `keywords`, and the tag filter reads only those; detail pages show six. Lead with the distinctive ones, and don't spend a slot repeating the category.

## README rendering (verified 2026-09-24)

- Plugin pages render each README with the site's own regex renderer, which covers only part of GitHub-flavoured markdown. Check any new markdown shape against GitHub: `gh api markdown --input -` with `{"text": "...", "mode": "markdown"}`. Mode `gfm` is comment mode and turns every newline into `<br>`, so its answers are wrong for a README.
- The READMEs share templates, so a rendering bug on one page is usually on many: the `---` footer rule printed as text on 24 of 31 pages. Count it across every `docs/plugins/*/index.html` before saying how far it reaches.
- After a CSS change, compare each page's README height at 375px, not only whether the page scrolls sideways. `overflow-wrap:break-word` split a word inside review-squad's table without any overflow; only the height change showed it.

## Plugin install paths (verified 2026-09-24)

- Give every skill its own folder, `skills/<name>/SKILL.md`. When a plugin has `skills/SKILL.md` and also `skills/<sub>/SKILL.md`, Claude Code loads only the top one (`claude plugin details <name>` shows `Skills (1)`), while `npx skills add` loads them all. A router skill that invokes `<plugin>:<sub>` then names skills Claude Code never loaded. `claude plugin validate` passes both layouts, so it won't warn you.
- Claude Code clones the plugin repo, so users get only tracked files, and runs `npm ci --ignore-scripts` only when `package.json` and a lockfile sit at the plugin root. It allows 60 s and carries on if that fails. No build or install script runs, so an MCP server whose command points into a gitignored `dist/` fails after `/plugin install`. Commit the build output, as speed-run does with `mcp/dist/`, and avoid packages that need an install script: sharp 0.32 crashed journal-mcp's server at startup, while sharp 0.33 ships its binaries as optional dependencies.
- Declare MCP servers in a root `.mcp.json` or under `mcpServers` in `.claude-plugin/plugin.json`. Claude Code ignores `type` and `mcp` keys. In `command`, `args` and `env`, an unset `${VAR}` stays as literal text; write `${VAR:-}` to pass an empty value.
- Bump `version` in `.claude-plugin/plugin.json` with every fix. Claude Code uses it as the cache key, so users who already installed get nothing until it moves. It wins over the marketplace entry's `version`. Users then run `claude plugin update <name>` (with or without `@2389-research`) and restart.
- `npx skills add` copies SKILL.md folders only: no hooks, MCP servers, commands or agents. A plugin that needs a hook or a server works in full only through `/plugin install`. Files a skill links outside its own folder, such as deliberation's `skills/shared/`, don't arrive either, so keep a skill's references inside its folder. Subfolders of that folder do arrive: skills CLI 1.7.0 copies it recursively, skipping only `metadata.json`, `.git`, `__pycache__` and `__pypackages__`. It installs each skill as a sibling folder named after its frontmatter `name`, lowercased with other characters turned to `-`, so a link into a sibling skill such as `../review/SKILL.md` survives only when that skill's name matches its folder name. The skills CLI needs Node 22.20 or later, so a CI job that runs npx needs Node 22. The skills CLI behind it also skips any SKILL.md whose `description` holds an unquoted `: ` ("Nested mappings are not allowed in compact mappings"), though Claude Code loads that file. Quote such values; when one holds both `"` and `'`, a `>-` block needs no escaping. Claude Code reads quoted and block descriptions alike.
- Judge `npx skills add … --list` by its own output, never by searching it for skill names. It prints `Found N skills`, puts each listed name alone on a line indented four spaces under the box rule, and warns `Skipped <path> — <reason>` on stderr, so a log that drops stderr can't show a skip. A name search passed test-kitchen's skipped `cookoff`, because two other skills' descriptions name it.
- `/plugin install <name>@2389-research` on a machine without the marketplace fails with "not found in marketplace … your local copy may be out of date". The fix is `/plugin marketplace add 2389-research/claude-plugins`, not an update.
- To test installs without touching your own setup, point `CLAUDE_CONFIG_DIR` at a fresh folder. To prove afterwards that `~/.claude` didn't change, copy the files you mean to check before you start and diff them at the end. Modification times aren't enough: on 2026-09-24 a Claude Code session on the real config (not a test run) refreshed `claude-plugins-official` in `~/.claude/plugins/known_marketplaces.json` mid-audit, and the saved times showed only that the file had changed, not what. On 2026-09-25 `settings.json` also lost its `model` key mid-audit, outside any test run, and a diff against the copy named both changes at once. To install an unpushed branch the way users get it, add a scratch marketplace whose entry has `"source": {"source": "url", "url": "file://<clone>", "ref": "<branch>"}`. `claude --plugin-dir <dir> plugin details <name>@inline` lists a working tree's parts without installing. It counts servers named by a path to `.mcp.json` but shows `MCP servers (0)` for ones inline in plugin.json, so check servers with `claude mcp list`. `DISABLE_TELEMETRY=1 npx -y skills add <owner/repo> --list` shows what npx would install without installing it.
- Before planning a fix to a plugin repo, list its open PRs. On 2026-09-24 all 11 repos with install bugs already had open PRs touching the same files.

## Plugin repo CI (verified 2026-09-24)

- A repo can give its workflows a write `GITHUB_TOKEN` by default; `gh api repos/<owner>/<repo>/actions/permissions/workflow` shows `default_workflow_permissions`. `actions/checkout@v4` saves the token in `.git/config`, so a plain `npm ci` after it hands the token to every dependency's install script. In a workflow that installs packages, set `permissions: contents: read` and checkout's `persist-credentials: false` instead of trusting the repo default.
- CodeRabbit reviews each repo alone. The two `scripts/check-plugin-install.mjs` files are identical, yet it flagged the `npm ci` timeout only in slack-mcp and the stdout parsing only in journal-mcp, so apply each finding to every copy.
- Pinning an action to a commit SHA (`actions/checkout@<sha> # v6.1.0`) is the only way to make it immutable, and Dependabot version updates still move such pins and their same-line comment. It costs vulnerability alerts: GitHub's security hardening guide says Dependabot "will not create alerts for actions pinned to SHA values".

## Plugin repo PRs (verified 2026-09-25)

- GitHub closes an issue *or a PR* when text that lands on the default branch puts fix, close or resolve, in any form or case, before `#N`. The July skill-audit PRs numbered their findings "Fix #2", so merging them closed newer PRs #2 in firebase-development (from a PR body) and git-repo-prep (from a commit message). Number findings "item 2" or "F2", and before merging, grep the PR body and its commits: `grep -niE '(close[sd]?|fix(e[sd])?|resolve[sd]?)[[:space:]:]+#[0-9]+'`.
- GitHub search's `closed:` qualifier left out one of those auto-closed PRs. To see what closed on a given day, read `gh api "repos/<owner>/<repo>/issues?state=closed&since=<ISO date>"`, which lists PRs too.
- A PR closed that way keeps its head branch, and `gh pr reopen <n>` brings it back. We reopened before pushing to the branch, which worked; pushing first is untested.
- When one PR edits a file and another moves it unchanged, GitHub can mark the second PR conflicting even though `git merge` follows the rename and merges cleanly (prbuddy #2 and speed-run #9). `git -c merge.renames=false merge-tree --write-tree origin/main <branch>` reproduces that conflict. Merge main into the moving branch yourself; the merge keeps the move and carries the edit to the new path. Pushing that merge cleared GitHub's flag on both.
- In `.claude-plugin/plugin.json`, a version-only bump conflicts with a PR that edits `description` (the line above) or adds a key after `version` (which puts a comma on the version line). After merging one of two PRs that touch the same files, merge main into the other before merging it.
- After a push, CodeRabbit's check sat PENDING for one to six minutes, and `reviewDecision` kept the APPROVED it gave the old head. On prbuddy #2 it then left a COMMENTED review on the new head whose one finding sat in the review body, under "Outside diff range comments", with no inline comment, so neither `reviewDecision` nor the PR's inline comments showed it. Before merging, read the newest review on the head commit (`gh pr view <n> --json reviews`), then merge with `gh pr merge <n> --merge --match-head-commit <sha>`, so a head that moved after your checks can't merge.
- Merging a workflow change with `gh pr merge` can need the token's `workflow` scope. GitHub refused Dependabot's #58 ("refusing to allow an OAuth App to create or update workflow … without `workflow` scope") once #57 had moved main, though the same token had just merged #57, whose branch was current. Bring the branch up to date first (`@dependabot rebase` for a Dependabot PR); the merge then goes through without the scope.
- A green CodeRabbit check can mean it never reviewed. Once the free OSS reviews ran out, the check on three new PRs read SUCCESS with the description "Review rate limited", beside a "Review limit reached" comment. Read the check's description (`gh api repos/<owner>/<repo>/commits/<sha>/status`) or CodeRabbit's summary comment before counting the check as a review.
